# EQ-06：兼容性、升级与发布质量

## 独立版本与数据保护

程序升级或回退不能覆盖、丢弃或错误解释用户已有的会话、知识与能力。

| 对象 | 管理要求 |
|---|---|
| 应用 | Electron、Host、前端及产品服务共同交付 |
| Pi SDK | 固定明确依赖版本，兼容验证后升级 |
| SQLite Schema | 独立有序迁移，不因应用更新重建数据库 |
| Skill | 独立安装、升级与回退，不绑定整个应用更新 |

应用更新不覆盖用户开发的 Skill，不破坏正式版本引用。描述性知识仍独立留存修订，不被应用版本或能力发布替代。

## Pi SDK 与 Session 兼容

既有关键实验以 Pi SDK 1.3.0 为主要基线，正式开发固定已测试版本。升级保留旧 SDK 与原始数据，使用新 SDK 加载测试，兼容通过后再正式切换。

复用已有集成用例检查：

- Session 历史树、`leafId`、Compaction 与恢复后继续执行。
- Tool、Extension、Skill 加载，以及 SDK 模式下必要的 `codemode`、`tool_search` 显式配置。
- Provider、Tool Calling 与生命周期事件行为。
- Reload 后 Tool 激活状态、会话连续性及多 Session 隔离。

Pi 对部分历史格式的迁移能力不构成未来所有版本兼容的保证。新 SDK 首次打开旧加密 Session 时，先保留旧快照，验证历史、分支及上下文恢复后再保存新格式，不能覆盖唯一旧副本。

不兼容时保留原始数据并报告问题，不能新建空 Session 冒充恢复成功，也不因一次升级重启架构选型。

## SQLite 迁移与应用回退

使用成熟迁移机制，明确结构版本及顺序；原对话提到 `PRAGMA user_version` 可记录应用格式版本，具体迁移仍由应用负责。

可事务化的迁移在事务中执行；升级前保留可恢复备份，失败不继续使用不完整结构。迁移不得破坏 Memory 来源、修正历史、分支背景与当前适用性。

应用回退不等于数据库可自动降级。优先保证相邻应用版本的数据兼容；旧应用不认识新结构时，阻止不安全的回退并提供明确恢复方式。不能直接以升级前整个数据库覆盖现有数据，丢失升级后形成的 Memory。

## Skill 与应用更新

Skill 沿用候选独立验证、等待安全空闲窗口、正式切换与失败回退。SDK 变化导致 Skill 不兼容时，保留文件和版本记录，明确兼容问题，必要时恢复已验证版本，不直接删除。

普通 `SKILL.md` 保持原生兼容，特殊 Skill 验证 Tool/Hooks 的 SDK 契约。复用 Pi Package 固定 npm 版本与 Git 引用能力，不另建包管理器。

桌面发布沿用 Electron 与 Forge 的成熟能力。默认后台检查及下载，当前任务继续；适当空闲时提示更新，安装前保存必要状态，之后恢复 Session、后台任务和 Skill。更新不得强制终止正在执行的 Host 任务；不新增灰度发布平台。

## 平台发布验收

| 平台 | 必须检查 |
|---|---|
| macOS | Developer ID 签名、公证、首次安装、XPC Worker、Pi Host、迁移与更新恢复 |
| Windows | 实际安装、Pi Host、原生依赖加载、AppContainer、迁移与更新恢复 |
| Web | 客户端与 Host 接口兼容、身份验证及断线重连 |

`better-sqlite3` 等原生依赖应在实际 Electron/Node 运行环境中加载验收。macOS 最小实验与 ad-hoc 签名不能替代正式分发验收；Windows 交叉构建不代表 Windows 运行或安全测试通过。

## 升级验收顺序

兼容性与安装包检查 → 确认当前任务能安全暂停 → 保存 Session 和业务状态 → 更新应用并迁移数据 → 重新加载 Pi、Skill、SQLite → 检查核心功能 → 正常继续或安全恢复。

该顺序只约束软件升级与数据保护，不规定 Agent 的思考流程。重启成功不能作为升级通过的充分条件；应实际确认旧 Session 可继续对话、Memory 可读、正式 Skill 可用、任务状态正确，安全 Worker 仍受限制。

安全恢复继续遵守 EQ-03，不因升级失败绕过加密、权限或版本验证，不盲目重放未知副作用。
