# EQ-05：性能、资源占用与长期运行稳定性

## 资源优先级

资源协调遵循：**正常 Agent 交互 > 正在执行的用户任务 > 用户授权的能力开发 > 自动 Reflection > 后台整理**。

该顺序控制执行资源，不规定 LLM 的分析流程。后台活动不能占满正常任务所需资源，诊断写入不能阻塞 Tool Calling；Skill 等待 Session 空闲时，也不能长期阻断用户新消息。

沿用单 Host、SQLite 持久化任务与 Node 定时调度，不重新开发任务系统。性能预算以实际模型、设备和任务成本为依据，不预设缺乏测量支持的内存、响应时间或 Token 限额。

## 运行资源管理

| 对象 | 质量要求 |
|---|---|
| Pi Session | 活跃会话保留运行资源，不活跃会话保存检查点后可释放，重新打开时恢复；不为全部历史常驻创建 AgentSession |
| 加密快照 | 在完整消息、Tool 完成等有意义的一致性边界保存，避免每个 Token 重写完整快照 |
| SQLite | 普通诊断事件可合并写入，重要业务状态及时事务提交；避免长事务、全表扫描和不必要的高频同步写入 |
| Reflection | Host 控制后台并发，可以排队但不丢失待处理任务；30 秒 Debounce 不等于资源调度 |
| Runtime | 正确释放旧 Session、Tool、Hook、订阅、计时器、IPC 与 Worker 资源 |

原对话区分 Compaction 的上下文压缩与完整历史保存：压缩不意味着历史不再占用内存。释放会话必须协调后台任务、在途 Tool 和未提交快照，不能简单按超时销毁或通过删除原始历史节省内存。

记录快照大小、生成及保存耗时、内存峰值。只有测量证明必要时才考虑增量持久化，不预先另造 Session 日志系统；写入频率仍满足 EQ-03，不能为速度牺牲已完成工作的可恢复性。

SQLite 检索沿用 FTS5。WAL 下单写入者、长读事务影响 Checkpoint，以及 `better-sqlite3` 同步 API 的交互阻塞风险，均按原对话作为测量重点。重型查询及批量写入应避开界面关键执行路径，不据此新增数据库服务或缓存层。

Reflection 具有自主分析能力，资源控制作用于并发和执行预算，不规定每次只能查询几条记录、使用固定 Token 数或按固定步骤分析。

## Host 与客户端稳定性

Electron 负责桌面生命周期和界面，Agent Host 是独立运行单元。TD-04 主进程运行 Pi 的原型证明可行，不据此要求最终产品所有工作都在主进程，也不要求每个 Session 一个进程。

- Host 异常不直接造成桌面窗口崩溃。
- 客户端重连不重建仍在运行的 Agent。
- Reflection Worker 故障不影响正常 Agent。
- 运行单元退出、Reload 与版本回退后正确释放资源，不累积失效引用或重复 Hook。

这里保留既有职责边界，不另行指定进程实现或新的基础设施。

## 性能与长期运行验收

先建立代表性基线，再确定合理预算，至少覆盖：

| 场景 | 观察内容 |
|---|---|
| 启动与空闲 | 启动耗时、空闲 CPU、常驻内存 |
| 长时间运行 | 内存趋势、进程数量、资源释放后的增长情况 |
| 多 Session 并行 | 响应延迟、任务隔离与资源竞争 |
| 大型 Session 恢复 | 快照大小、恢复耗时与峰值内存 |
| 大量 Memory 和 Log | 查询延迟、数据库及 WAL 增长 |
| Reflection 与用户任务并行 | 对正常交互的影响 |
| Skill 多次更新及回退 | 旧 Runtime 释放、重复 Hook 和引用残留 |
| 客户端反复关闭与重连 | 重复订阅、任务和进程 |

连续 24～72 小时创建会话、执行 Tool、触发反思和切换 Skill，是原对话给出的初始稳定性场景示例，不是产品使用门槛或未经测量的服务承诺。关注释放资源后的持续增长，不能仅比较运行前后两个内存数值。

不为性能删除原始历史、限制正常推理或削弱持久化和安全要求。SQLite、原生 Compaction 与轻量调度能够满足需要时，不提前增加 Redis、独立队列、向量数据库或自研上下文系统。
