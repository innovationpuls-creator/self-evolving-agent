# SA-08：系统架构审查与收口

## 最终逻辑边界

| 边界 | 职责 | 方向 |
|---|---|---|
| Pi Runtime | Agent Loop、模型、Session、Tool Calling | 原生复用 |
| Skill 扩展 | 知识、指导、脚本、Hooks 与能力管理 | 基于 Pi 扩展 |
| Diagnostic Log | 高价值诊断、查询及原始证据定位 | 补充原生信息缺口 |
| Memory | 长期认识、修正、Global/Project 作用域 | 优先复用成熟扩展 |
| Reflection | 自主分析与描述性知识更新 | 特殊 Skill 承载认识方法 |
| Evolution | 建议、授权、验证开发、能力生效 | 扩展原生 Agent 使用方式 |
| 产品运行与客户端 | 后台活动、多会话、连接与 Web/桌面交互 | 补充产品协调能力 |

这描述职责，不要求七个独立服务。在架构阶段收口时，技术可行性尚未全部确认；后续结论见第六阶段。

## 架构审查结论

1. **Skill 不是全能运行容器。** Skill 组织知识与能力，Extension 连接可执行行为，Pi 执行原生调用；不同内容不必同时加载或更新。
2. **Session 不等于完整诊断系统。** 它是主要原始证据源，Skill 加载、嵌套调用、版本关联等缺口需实证判断，只补高价值信息。
3. **Extension 不等于安全边界。** Prompt、工作目录、前端隐藏或模型不可见不能替代实际权限与隔离。
4. **原生安装与完整安全保证分开。** 自进化核心以 Pi Package 原生兼容与独立安装为目标；严格敏感信息保护与权限隔离依赖满足既定约束的受控运行环境，不能仅由普通 Extension 保证。专用 Web/桌面端提供完整交互，但不是核心使用前提。
5. **Memory 不等于当前会话状态。** 回档不自动撤销外部知识，需识别来源、分支与适用性，不能继承已废弃项目决定。
6. **恢复历史不等于安全重放。** 不能确认副作用是否完成的操作，不盲目再执行。

优先不改 Pi Core、不重写现有机制；但不改 Core 不能优先于已确定的强制脱敏、真实隔离与可靠执行要求。若条件冲突，依据技术证据重新评估方案。

## 后续技术验证：TD-01

以下保留架构阶段结束时提出的四项验证目标，不表示当时已经实施；本篇不预先锁定数据库、框架或隔离方案。后续验证与最终技术选择见[第六阶段：技术决策](../README.md#技术决策)。

### P0-01：原生 Session 的敏感信息保护

追踪从生成到持久化的完整写入路径，核对 SDK/Extension 在写入前的实际控制范围，分别评估 CLI 与 SDK。

覆盖消息、参数、结果、系统提示与 Tool 声明等实际记录，验证保护不会破坏正常 Tool 执行和后续历史恢复。

**通过标准：** 使用模拟凭证，正常执行、会话恢复、上下文压缩和历史导出过程中，受保护数据不出现明文测试凭证。若只有 SDK 能保护，必须明确 CLI 限制。

### P0-02：执行权限与隔离

检查 Reflection 能否只读执行信息、写入指定描述性知识，而不能改变正式 Tool、Hooks 和长期行为规则。

覆盖基础文件工具、Extension Tool、codemode、嵌套调用、脚本及子进程。不能以提示词或单个 tool_call Hook 代替实际资源限制。

**通过标准：** 模拟未授权修改不影响受保护能力；原生机制不足时指出缺失的边界，暂不预选沙箱技术。

### P1-01：特殊 Skill 的动态管理

验证注册、发现、加载、启停、更新及运行中版本一致性。检查 direct、codemode、deferred、hidden 的实际调用路径和作用，不把隐藏等同于禁用。

核对 Hooks 取消订阅、重载、重复注册，以及多个 Session 观察到的能力一致性。

**通过标准：** 特殊 Tool 可真实使用，禁用后不可直接或间接调用，更新不会意外影响已有执行，Hooks 不重复生效。

### P1-02：Session 与后台反思

核对 agent_settled 等生命周期事件是否支持既定 30 秒规则，连续消息时能否可靠识别稳定结束。

验证独立 Reflection Session、跨会话历史查询、Session 切换、Extension 重载、进程退出恢复及可获得的诊断信息。

**通过标准：** 生命周期和历史能力有证据支撑既定规则，清楚说明可恢复与不可恢复的状态；本项验证不等于开发完整反思系统。

## 验证报告的判定方式

| 结论 | 含义 |
|---|---|
| 原生满足 | 已有原生能力完整覆盖 |
| 扩展满足 | 不修改 Core，通过实际 SDK/Extension 能力覆盖 |
| 部分满足 | 有可复用能力，但存在明确限制 |
| 无法满足 | 有证据表明存在阻碍，需要调整方案 |
| 尚未验证 | 证据不足，不作能力结论 |

每项报告应给出源码位置或实际 API、必要的最小实验结果、限制、是否需修改 Core、推荐方向及理由，并记录实际测试版本和 Commit。

“理论上可用 Extension 实现”不是验证通过。SDK/CLI 必要能力一致性、多 Session 共享资源与后台恢复也要在相关项目中明确；验证结果应允许推翻早期假设，再进入具体技术决策。
