# SA-02：核心能力解耦与协作

## 六项核心职责

| 能力 | 负责 | 不负责 |
|---|---|---|
| Pi Runtime | 执行、模型、Session、Tool Calling | 项目特有反思逻辑 |
| Skill Runtime | 特殊 Skill 解析、Tool/Hook 接入、启停 | 日志和长期记忆存储 |
| Diagnostic Log | 采集事实、结构化指标、关联证据、查询 | 判断行为是否合理 |
| Memory | 知识持久化、检索、修正和来源关联 | 执行脚本或管理 Tool |
| Reflection | 自主认识审查、知识更新、能力构想 | 底层采集与未经授权的正式变更 |
| Evolution | 建议、授权、开发活动与版本生效 | 代替 LLM 设计实现方案 |

这是能力分工，不要求六个独立服务。产品运行与客户端负责必要的生命周期协调、交互和反馈，不再持有一套重复业务规则。

## Agent 按需协作

普通 Agent 与 Reflection 复用信息访问与 Tool Calling 机制，分别遵守各自活动的执行权限。需要分析效率时查询诊断，需要核实依据时读取原始 Session，需要旧认识时查询 Memory，需要理解能力时读取 Skill。

访问顺序、范围和次数由 Agent 决定，不把全部资料预拼到 Prompt，不为 Reflection 另建工具调用系统。

## 自进化 Skill 与基础扩展

基础扩展提供事件监听、触发管理、查询、知识读写、可执行能力接入和权限检查接入。真实的权限隔离与严格敏感信息保护依赖满足既定约束的受控运行环境，不能仅由普通 Extension 的检查逻辑保证。自进化 Skill 提供理解运行信息、认识能力边界、审查知识与提出构想的方法指导。

这样反思方法可持续更新，而底层运行、数据与权限不集中在一个 Skill 中。

## 独立性约束

- 关闭反思不停止日志采集，也不影响已保存 Memory 的查询与管理。
- 反思可以分析已结束会话的历史，不要求原 Session 仍活动。
- Reflection 不拥有其他模块的内部数据，通过可用能力按需访问。
- 更换 Memory 实现不应要求重写 Reflection。
- 日志记录事实；反思解释事实；二者不互相替代。
- 正式修改由资源和执行权限限制，不能只靠 Tool 可见性或 Skill 文字约束。

版本、知识与局部结果分别管理；故障传播与结果反馈见 SA-06。
