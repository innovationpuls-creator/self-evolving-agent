# TD-06：数据持久化方案

## 最终决定

采用 **Pi 原生 Session + SQLite 产品业务数据库**，职责独立。此分工由用户明确提出并在 TD-06 收口，不把 SQLite 变成另一套执行历史系统。

| 数据 | 权威存储 |
|---|---|
| 对话、Tool 参数与结果、分支、Compaction | Pi 原生 Session 结构，宿主加密快照保存 |
| Global / Project Memory | 产品 SQLite |
| Reflection、Evolution Suggestion 与开发状态 | 产品 SQLite |
| 后台任务状态、Skill 版本元数据 | 产品 SQLite |
| Diagnostic Log | 产品 SQLite，仅保存轻量诊断与证据引用 |
| Skill 代码、脚本与资源 | 独立版本文件，SQLite 保存引用和状态 |

JSONL 是原生会话格式，不要求正式产品以明文 JSONL 落盘。Session 沿用 TD-05 的内存运行、加密快照及原生恢复。

## Diagnostic Log 边界

Pi Session 已保存完整参数与结果，SQLite 不复制一遍。诊断侧保存 Session、Trace、Entry 等证据引用，以及必要的 Tool 名称、耗时、调用状态、输出规模特征和 Skill 版本关联。

Agent 先查轻量诊断，再按需访问原始历史。诊断事实与长期认识分开，不重复保存完整上下文；具体范围沿用 RE-04，不借选型扩充采集。

## SQLite 选择与取舍

使用一个产品 SQLite 数据库，内部按业务职责分离。相关状态以事务共同提交，普通索引和 FTS5 优先满足查询，语义检索只在必要时增强。

TD-08 后续确定 `better-sqlite3` 为当前首选，采用 WAL；`node:sqlite` 保留备选。单 Host 原型支持该路线，不代表 Electron 目标 ABI 已兼容。

首版不要求独立数据库服务、Redis、消息队列或向量数据库，减少单用户产品的部署依赖。SQLite 不接管 Pi 的会话树、上下文与压缩。

## 安全与一致性

SQLite 不默认提供应用层加密，敏感内容仍遵守既定保护要求。采用数据库不允许凭证明文进入 Memory、诊断或异常记录。

SQLite 事务只覆盖数据库操作，不能自动使 Session 快照、Skill 文件及外部 Tool 副作用共同原子提交。恢复、发布和中断处理分别依 TD-05、TD-10、TD-08，不把数据库事务解释为外部 exactly-once。

## 可行性与限制

TD-06 是存储分工决定，没有独立产品数据库实现报告。后续依据包括原对话的 TD-07 Memory 评估，以及 [TD-08 SQLite 调度实验](../../experiments/pi-background-jobs/REPORT.md)。

这些材料支撑 SQLite/FTS5 和单 Host 路线，不代表正式 schema、完整迁移、备份恢复或 Electron 集成已实现。本项不补写数据库结构。
