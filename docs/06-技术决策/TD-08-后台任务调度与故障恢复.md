# TD-08：后台任务调度与故障恢复

## 最终方案

采用 **单 Agent Host + SQLite + Node.js 定时调度 + Pi 原生 AgentSession**。SQLite 保存任务事实，Host 负责登记、合并、认领及恢复，Pi 执行实际 Agent 活动；客户端只查看和操作。

`better-sqlite3` 为当前首选，`node:sqlite` 保留必要时的备选。不引入 Redis、独立队列服务或工作流框架。

## Reflection 调度

| 环节 | 规则 |
|---|---|
| 触发 | 普通 Session 的 `agent_settled` 仅登记任务，不在 Hook 中等待模型 |
| 计划时间 | 最后一次有效触发后 30 秒 |
| 合并 | 仅合并同一 Session、同一有效分支内的未开始任务，更新来源与计划时间；不同 Session 或不同分支独立调度 |
| 执行 | 到期后事务认领，再创建独立 Pi Session |
| 运行中又有活动 | 不覆盖正在运行的 Reflection；同一 Session、同一有效分支的新活动可合并为 pending follow-up，其他来源独立调度 |
| 防止递归 | 后台 Session 不加载普通任务登记扩展，Reflection 结束不触发自身 |

新消息更新或取消尚未执行的安排；用户主动结束或切换会话可按既有规则提前安排。关闭窗口不等于会话结束，客户端退出也不应取消 Host 中的任务。

调度器决定何时执行，不规定反思方向或要求每次产出知识。正常用户任务优先，Host 使用简单可配置的并发限制；原型采用单 Worker 串行执行，不代表已验证多 Agent 并发。

任务合并范围与分析范围独立。Reflection 可以自主跨会话读取历史，但不能据此合并不同 Session 或不同分支的待执行任务。

## 持久化与中断恢复

产品状态需能区分等待执行、运行、等待用户、完成、失败和中断；原型具体记录 `pending/running/succeeded/failed/interrupted`，没有验证等待用户的完整产品流程。

任务具有稳定 ID、来源及计划时间。Node timer 只唤醒，SQLite 才是事实来源；Host 重启重读 pending 任务，不能依赖丢失的内存计时器。

原型在启动时把遗留 running 标记为 interrupted，停止自动重放。Tool 可能已经修改文件或调用外部服务，而完成记录尚未写入；SQLite 事务不保证外部副作用 exactly-once。检查实际结果后才能确定恢复方式，不能仅把状态改回 pending。

## 可行性依据

[TD-08 报告](../../experiments/pi-background-jobs/REPORT.md)及[保存结果](../../experiments/pi-background-jobs/results/last-run.json)基于 macOS arm64、Node 26.10.0、Pi SDK 1.3.0、better-sqlite3 13.0.3，使用 Faux Provider。

原型验证 30 秒去重、客户端退出后 Host 留存、pending 经 SIGKILL 后恢复、独立 Session、防递归及中断识别。模拟副作用先写入独立文件，随后进程被杀；恢复后未再次调用 Tool，记录仍只有一条，数据库完整性检查正常。

该历史原型按 Project 合并 pending 任务，仅作为当时的实现与证据保留；它未验证上述同一 Session、同一有效分支的产品合并边界，不作为扩大任务合并范围的依据。

到期后 1 ms 启动只是单次结果，不是产品实时性承诺。WAL 与 `synchronous=FULL` 是该实验使用的设置，不等于全部产品数据恢复已验收。

## 风险与限制

只验证本地单 Host；多 Host、网络文件系统和高吞吐未测，不能直接推广启动时处理全部 running 的恢复规则。

Electron 中原生 addon 的 ABI、签名及加载未验证；远程 API、任意脚本副作用、真实 Reflection/Memory、设备休眠和时钟跳变也未覆盖。现有证据证明未知结果不自动重放，不证明任意操作恰好执行一次。
