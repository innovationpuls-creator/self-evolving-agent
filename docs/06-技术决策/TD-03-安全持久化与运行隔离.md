# TD-03：安全持久化与运行隔离

## 最终运行边界

采用 **Pi 原生 Runtime + 宿主安全持久化**；已验收 Reflection 保持独立受限 Worker。Pi 负责原生推理、Tool Calling 和 Session；Host 管理存储、凭证、业务状态及产品权限。D4 不额外要求沙箱。

| 活动 | 边界 |
|---|---|
| 正常 Agent | 保留用户授权的工作环境和宿主能力 |
| 自动 Reflection | 读取允许的历史与知识，通过受控入口提交知识更新和进化建议 |
| 授权 Evolution | 在目标范围内开发、管理依赖和测试，与正式能力隔离，验证通过后发布 |

活动复用 Pi Agent 机制。自动 Reflection 保留特定受限操作通道；正常 Agent 与授权 Evolution 使用当前用户权限，产品不宣称它们彼此具有 OS 级文件/进程隔离。

## 持久化方案的收敛

执行数据保持原样，不为保存或导出而改写执行中的消息。活跃 Session 使用 `SessionManager.inMemory()`，宿主接管保存与恢复。

TD-03 初期提出保存前脱敏，TD-05 将恢复与传播分开：

- **恢复入口：** 完整原始快照采用 AES-256-GCM 加密，保留原生条目和选中分支。
- **数据传播：** Diagnostic Log、Memory、客户端、导出和模型请求遵守敏感信息检查与脱敏要求。
- **安全导出：** 使用独立副本，不写回活跃会话，不当作可恢复快照。

加密不能阻止解密后的无关秘密进入模型或客户端，脱敏也不能破坏真实 Tool 参数。密钥与恢复细节集中在 TD-05。

## 隔离方案的取舍与修订

Docker/OCI 与 D4 独立 VM 不作为产品必需能力。桌面产品内置 Pi/Node 运行环境，不要求普通用户另装 Node.js、Pi CLI 或 Docker。

D3 已采用 TD-12 的 **Electron Host → 固定 XPC Service → App Sandbox Node/Pi Worker**，属于 Reflection 当前可用实现而非 D4 前提。Windows Reflection 的对应路径仍需实机验证；普通 Evolution 使用 Pi 原生开发工具。

Reflection 不直接获得整个 Skill 目录写权限或覆盖正式 `SKILL.md`；Host 校验允许的知识候选后提交。知识与行为规则相邻，不意味着允许写知识就允许修改正式规则。

## 凭证与模型通道

凭证由 Host 管理，不把真实 API Key 无条件注入 Worker。TD-13 复用 Pi Native Provider，经有限 XPC 请求由 Host 调用授权模型；Worker 不因此取得任意网络、文件代理或原始凭证。

开发授权仅针对讨论确定的目标与受管 Skill 版本。生成代码按现有用户权限运行的风险必须明确；发布必须通过必要验证与既有版本切换机制。

## 可行性与剩余风险

安全持久化、macOS 最小沙箱及 Faux 模型通道分别有原型依据，见 TD-05、TD-12、TD-13；它们支撑路线选择，不等于跨平台正式安全验收。

Windows Reflection 受限运行、正式签名与公证等仍按对应阶段验收；D4 不再要求生成代码及多语言脚本的 OS 沙箱，不能把现有版本与候选验证描述为恶意代码安全隔离。
