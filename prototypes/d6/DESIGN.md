# D6 第二轮 · 两条设计路线与设计体系

第一轮方案没有通过验收。本轮不把它当作正确基础：重建工作区和业务组件，保留脱敏案例与已验证的状态语义。正式产品未改动；用户尚未批准任一方向。

## A：会话书桌

**持续工作是组织中心。** 最近会话、项目目录和长期积累入口保持在一条安静的侧栏。对话按请求→结果→关联变化阅读；长文在独立阅读区滚动，输入始终可用。一次工作留下的认识、反思与建议在结果之后出现，而不变成常驻监控卡片。

- 轨迹以执行叙事组织，逐次调用与右侧检查内容并列。
- Memory 像有目录的知识读本：左边识别对象，右边首先阅读当前认识；历史另用比较视图。
- Reflection 是回顾日志：稳定的结论标题、观察、待确认部分、对知识和能力的影响。
- 建议是一份需要判断的论证。进入独立讨论后，用户另行发送；授权在聚焦对话框中审阅。
- 能力库以用途目录进入，说明、文件、候选、工具归属、信任和版本各有适合的表面。

优点是当前目标连续、阅读节奏稳定、上下文代价较低。代价是跨会话比较属性需要进入索引，长期维护不是默认首屏。适合以完成日常工作为主、偶尔维护 Agent 的使用方式。

## B：工作册

**工作、认识与能力是三个平等的长期工作空间。** 顶部只表示目的，左侧目录随空间变化。这里的“工作”仍是已有 Session，没有另造任务管理实体。

- 工作结果与原始对话分别阅读，结果旁保留材料覆盖、关联认识和下一项决定。
- 轨迹先建立调用登记表，再进入选中的记录；选择后定位阅读区，保留返回目录。
- Memory 用登记册比较性质、范围、状态和最近修订，再深入选中认识。
- Reflection 按时间立档，观察与不确定性在宽窗口并列，变化关联仍有独立位置。
- 能力目录采用用途与状态矩阵，候选与正式内容仍分开；选择能力后进入对应阅读位置。
- 建议队列、活动阶段和讨论背景保留在工作区。开发授权进入独立决策页，允许来回核对背景与范围。
- 设置是“工作环境”目录，不挤入日常会话控制。

优点是对象属性和长期关系容易发现，适合经常审查认识与维护能力的用户。代价是目的层、目录和阅读区需要学习；目录→阅读的定位必须明确。窄窗口收束为目录/对象切换，避免保留三列。

## 不是两套主题

两套共用模拟数据、Markdown/代码/JSON、按钮和权限语义；分别实现会话顺序、结果出现时机、轨迹组织、知识目录、能力目录及授权表面。A 的轨迹是左右叙事，B 是登记表后进入记录；A 的 Memory 是常驻阅读页，B 是跨对象登记册；A 授权是对话框，B 是独立工作区。仅共享高质量的业务内部内容，不用 CSS 调换元素顺序冒充路线差异。

## 布局与阅读关系

- 全局框架只承担位置、导航与连接。A 侧栏230px，B 232px；中窗口逐步降到178–200px；700px以下使用可收起目录。
- A 会话正文约790px，超宽窗口840px；CJK 正文16px、1.9行高。B 结果与关联信息并列，正文13px、1.95行高，适合密集审查。二者都控制段落与代码的独立滚动。
- 页标题25px，业务结论20px，正文/章节16px，控件/元信息约13px。主比例为1.25，13/16/20/25取整；10–11px仅用于时间、位置和非正文辅助信息，不能承载唯一错误或权限说明。
- 三种字重：400阅读，500对象与操作，600结论。大部分层次由位置、宽度、间距和分隔形成，不靠全面加粗。
- 4/8px基础空间；同对象内部8–12px，区块16–24px，业务章节28–32px。正文不为凑密度压缩行距。
- 分隔线说明对象、章节或状态边界。背景只用于选中、编辑、结构内容和需要注意的状态；不把每段文字放进卡片。
- 半径4px用于控件，6px用于轻量浮层，8–10px用于需要聚焦的对话框与输入容器。对象属性行没有独立圆角。

## 颜色与材质

A 采用纸面中性色和低饱和绿色，B 采用偏冷的目录中性色和蓝色。两者的正/负/未知语义相同：绿色表示已有肯定证据，赭色表示等待或覆盖边界，红色表示已发生的失败，灰色表示未知或普通状态。执行结束不自动使用绿色成功标记。

表面不使用玻璃模糊、装饰渐变、统计卡片或大面积品牌色。图标来自 Lucide，只提供辨识与方向，不给所有文本附图标。系统字体服务跨 Web/Desktop 一致性，没有外部字体请求。

## 控件与反馈

详见 [组件清单](UI-INVENTORY.md)。这是实际实现规则，而非仅有 Token 表：

- 当前主要动作使用实心，次要操作使用描边，同对象辅助操作使用文本；不能同时出现一排同权重实心按钮。
- Hover 不改变尺寸；focus ring 清楚区分键盘焦点；选中状态不依赖 hover；禁用按钮保留动作名称与位置。
- Dialog/Menu/Tabs/Tooltip 使用 Radix 无样式基础设施；原生 Input/Select/Details 保留浏览器语义。对话框 Tab 不离开，Escape 返回触发位置。
- 普通反馈100–140ms；运行只用轻量状态点或旋转；不制造阶段百分比。所有动效尊重 reduced-motion。
- 读取、执行、授权、检查与生效分别呈现。错误说明原因、已保留什么与下一步。重要状态不能只存在 Toast。
- 模块保持已选对象、页签和阅读位置；来源可在 Drawer 查看，全局返回可回前一个模块。窄窗口有明确目录返回。

## 参考研究如何落地

| 研究来源 | 观察到的原则 | 本轮采用 | 没有移植 |
|---|---|---|---|
| [Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls) | 布局应建立层级与稳定关系；深入细节不应挤掉常用工作 | 输入常驻；对象阅读与可选详情分工；窄屏保留目录返回 | 系统玻璃材质、平台专属装饰 |

| [Linear Triage](https://linear.app/docs/triage) | 待决定事项先审视，再进入工作流程 | 建议可忽略、恢复；采纳只进入讨论 | 团队分配、自动优先级、任务管理实体 |

| [Highlight.js](https://highlightjs.org/) | 已知语言按需注册，原文与高亮分开 | TS/JS/JSON/Markdown 高亮，未知语言保留纯文本 | 全语言自动探测及外部 CDN |

## 需要用户裁决

1. 默认中心：A 的连续会话，还是 B 的长期工作空间。
2. 结果：按对话顺序，还是报告与原始对话分开阅读。
3. Memory/能力：常驻左右目录，还是先跨对象登记再聚焦阅读。
4. 授权：聚焦对话框，还是独立决策工作区。
5. 视觉密度：A 的16px阅读尺度，还是 B 更紧凑的目录与结果密度。

建议先比较同一模块的两种组织，再决定是否有必要组合。组合也需要重新确认整体导航，不能直接拼接所有入口。本轮没有正式方向推荐的既定结论，更没有获得正式前端实施授权。
